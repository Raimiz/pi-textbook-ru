# ADR 010：用换行作为会话记录的提交边界

- 状态：已采纳，等待 Chapter 10 学生与陪练复测
- 日期：2026-07-18
- 适用范围：`packages/pi-course/src/session.ts`

## 背景

Chapter 10 要把已经完成的消息保存成一棵追加式会话树。学生需要同时理解三件事：

1. 一次 `append()` 在什么时刻取得调用者数据的快照；
2. 哪些磁盘字节已经构成一条提交记录；
3. 写入可能只完成一部分时，同一个 writer 还能不能继续工作。

课程只承诺单进程、单个 writer 实例内的顺序。它不实现多进程锁、`fsync`、断电原子性
或自动修复。

## 决定

1. 每条记录使用一行 JSON；末尾换行是这条记录的提交边界。
2. `append()` 在调用时完成运行时校验、深复制和序列化，然后才把固定字符串放入
   FIFO。调用者随后修改原对象，不会改变待写入内容。
3. 以换行结束的记录一旦出现 JSON 或 schema 错误，读取立即失败并报告行号。
4. 文件末尾没有换行的部分一律视为未提交尾部。读取返回此前的完整记录和结构化
   warning，不猜测它是崩溃、人工编辑还是其他原因造成的。
5. 打开含未提交尾部的文件后可以只读恢复，但不能继续追加；修复或截断留给后续能力。
6. 一次底层追加失败可能已经写入部分字节。当前 writer 因此进入 `tainted` 状态：
   后续读取和追加都返回最初的写入错误，也不会再次调用底层写入。恢复必须创建新
   writer，重新检查文件。
7. `pathTo()` 先检查全库 `id` 唯一，再只检查所选 leaf 的祖先链。未选中分支的完整性
   不属于这个函数。
8. 从路径恢复消息时跳过 metadata，保留完整的消息块、工具调用和工具结果，不先投影
   成纯文本。

## 为什么这样选

把换行当提交边界后，恢复规则只依赖文件中已经存在的字节，不需要猜测“看起来完整”
的末尾 JSON 是否真的写完。writer 失败后停止工作，则避免第二次追加把可识别的断尾
拼成一条已经换行的坏记录。

另一种做法是自动截断断尾并继续写。它更方便，但需要额外定义修复权限、备份、并发
写入和截断失败；这些复杂性会遮住本章要学习的追加日志不变量。

## 代价

- 遗失最后一个换行但内容完整的 JSON 也会被当成未提交记录；
- 调用者必须显式修复断尾后才能继续写；
- 当前设计只能证明单实例 FIFO，不能证明多 writer 安全或数据已经刷入物理介质。

这些限制必须出现在 Chapter 10 的“本章没有证明什么”中，不能由测试通过推导出更强
承诺。
