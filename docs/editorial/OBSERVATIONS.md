# Наблюдения по Pi Textbook

Этот файл — инженерный дневник совместного чтения книги.

Здесь фиксируются выводы о педагогике, архитектуре Pi, эволюции решений и связях с другими агентными системами. Наблюдения не являются частью перевода и не выражают позицию автора, если это прямо не подтверждено текстом.

## Правила

- Отделять факт из книги от нашей интерпретации.
- Указывать главу или фрагмент, на котором основано наблюдение.
- Не переносить наблюдение в авторский текст без отдельного решения.
- Не превращать файл в коллекцию общих мыслей об AI.
- По возможности формулировать, чем наблюдение полезно для понимания курса.

## Формат

```markdown
## Наблюдение N — Название

**Основание:** глава, раздел или фрагмент.

**Тип:** педагогика | архитектура | терминология | сравнение | вопрос

**Наблюдение:** вывод.

**Почему это важно:** значение для понимания курса или будущего предисловия.

**Статус:** предварительное | подтверждается | пересмотрено
```

## Наблюдение 1 — Pi как средство изучения агентной инженерии

**Основание:** структура курса и описание главной страницы.

**Тип:** педагогика

**Наблюдение:** Pi Textbook выглядит не столько курсом по использованию готового Pi, сколько курсом по инженерии LLM-агентов. Pi служит референсной реализацией, на которой архитектура строится снизу вверх.

**Почему это важно:** русское предисловие должно объяснить, что ценность книги шире конкретного инструмента.

**Статус:** предварительное

## Наблюдение 2 — Абстракция появляется после проблемы

**Основание:** заявленная последовательность: офлайн-агент, потоковая обработка, Tool Calling, Agent Loop, дерево сессий, сжатие контекста, runtime.

**Тип:** педагогика

**Наблюдение:** курс не вводит крупные абстракции заранее. Сначала читатель сталкивается с ограничением текущей реализации, а следующая глава добавляет механизм как ответ на конкретную проблему.

**Почему это важно:** это сильный педагогический приём. Перевод должен особенно бережно сохранять переходы «проблема → необходимость → решение».

**Статус:** предварительное

## Наблюдение 3 — Каждая глава делает предыдущую архитектуру недостаточной

**Основание:** общая структура курса.

**Тип:** архитектура

**Наблюдение:** главы образуют не набор независимых возможностей, а эволюцию одной системы. Каждая следующая возможность появляется потому, что прежняя версия уже не справляется с новым требованием.

**Почему это важно:** локальный перевод отдельной главы нельзя выполнять без понимания её роли в общей архитектурной линии.

**Статус:** предварительное

## Наблюдение 4 — Минимум маркетинговой лексики

**Основание:** главная страница и структура курса.

**Тип:** терминология

**Наблюдение:** автор опирается на инженерные понятия — состояние, поток, цикл, слой, тест, runtime — вместо рекламных формул об автономности и революционности AI.

**Почему это важно:** русская редакция не должна добавлять пафос, которого нет в оригинале.

**Статус:** подтверждается

## Наблюдение 5 — Checkpoint как часть метода обучения

**Основание:** формулировка о checkpoint после каждой главы.

**Тип:** педагогика

**Наблюдение:** checkpoint — не просто удобство Git или снимок кода. Он делает каждый этап воспроизводимым, позволяет сравнить архитектуры и вернуться к версии до появления новой абстракции.

**Почему это важно:** в книге соединяются объяснение, код и проверяемое состояние проекта.

**Статус:** предварительное

## Наблюдение 6 — Тесты фиксируют архитектурные инварианты

**Основание:** заявление о проверке ключевых сценариев и инвариантов тестами.

**Тип:** архитектура

**Наблюдение:** тесты в курсе, вероятно, используются не только для проверки функций, но и для сохранения свойств агента при усложнении runtime.

**Почему это важно:** при переводе тестов и их описаний нужно понимать, какой инвариант они защищают, а не только переводить строку.

**Статус:** предварительное

## Наблюдение 7 — Ошибка должна указывать на слой

**Основание:** формулировка главной страницы: «Любая ошибка должна указывать на конкретный слой системы».

**Тип:** архитектура

**Наблюдение:** курс рассматривает диагностируемость как архитектурное свойство, а не как дополнительную функцию после реализации агента.

**Почему это важно:** это может стать одной из центральных тем будущего предисловия: хороший agent runtime должен объяснять собственные сбои.

**Статус:** подтверждается

## Вопросы для проверки по мере чтения

- Как автор определяет границу между Agent Loop и runtime?
- Является ли дерево сессий структурой сообщений, состояний или событий?
- Какие именно инварианты закрепляются тестами?
- Где проходит граница между working memory и историей сессии?
- Сжатие контекста является частью runtime или отдельным слоем?
- Насколько архитектура курса совпадает с актуальной реализацией Pi?
